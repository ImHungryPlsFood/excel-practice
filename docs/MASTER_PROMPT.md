너는 지금부터 시니어 풀스택 엔지니어, 프로덕트 디자이너, UX 애니메이터, 교육과정 설계자, 데이터 분석 전문가, QA 엔지니어의 역할을 동시에 수행한다.

내 목표는 단순한 엑셀 강의 사이트를 만드는 것이 아니다.

**초보자가 스프레드시트를 처음 접하는 순간부터 실제 회사 업무, 고급 데이터 분석, Excel 관련 대회, 컴퓨터활용능력 자격증 대비까지 단계적으로 성장할 수 있는 웹 기반 실습 교육 플랫폼을 만드는 것**이다.

나는 Claude Code를 사용해 실제로 개발하고 배포할 것이다. 따라서 디자인 시안이나 설명만 제시하지 말고, 프로젝트 파일을 직접 생성하고 코드를 작성하며, 실제로 실행하고 테스트하면서 완성해라.

프로젝트를 진행할 때 아래 요구사항을 반드시 지켜라.

# 1. 제품의 핵심 철학

이 서비스는 다음 네 가지를 결합해야 한다.

1. Duolingo에서 영감을 얻은 명확한 학습 경로, 목표, 진행도, 성취 시스템.
2. Chess.com의 퍼즐에서 영감을 얻은 문제 해결 중심 학습, 단계적 힌트, 난이도 조절, 오답 복습.
3. 실제 게임 튜토리얼에서 볼 수 있는 화면 강조, 자연스러운 말풍선, 단계별 안내, 부드러운 전환.
4. 실제 스프레드시트 프로그램에서 사용하는 셀, 행, 열, 수식 입력, 서식, 차트, 데이터 처리 등의 작업 환경.

단, 기존 서비스의 화면, 로고, 캐릭터, 문구, 디자인을 그대로 복제하지 마라. 각 서비스의 장점을 분석하고 독자적인 브랜드와 UX를 설계하라.

이 서비스의 가장 중요한 차별점은 다음과 같다.

**사용자가 설명을 읽는 것만으로 학습을 완료할 수 없어야 한다. 실제 스프레드시트에서 직접 작업하고, 그 작업이 올바른지 검증받아야 한다.**

예를 들어 사용자가 SUM 함수를 배우는 경우 다음과 같이 진행한다.

- 먼저 합계가 무엇인지 짧고 명확하게 설명한다.
- 실제 스프레드시트와 비슷한 작업 화면을 보여 준다.
- 주변 UI를 자연스럽게 어둡게 만들고, 필요한 셀이나 수식 입력 영역을 강조한다.
- 사용자가 직접 셀을 선택하고 수식을 입력하도록 한다.
- Enter를 누르면 입력 내용을 검증한다.
- 정답이면 자연스러운 시각적 피드백을 제공한다.
- 오답이면 구체적인 오류를 설명하고 재도전하게 한다.
- 사용자가 원할 때만 단계별 힌트를 제공한다.
- 해결 후에는 왜 그 방법이 맞는지 짧게 설명한다.
- 다음 문제에서는 같은 개념을 다른 실무 상황에 적용하게 한다.

모든 기능은 이러한 학습 철학을 중심으로 설계해야 한다.

# 3. 권장 기술 스택

기본적으로 다음 기술을 우선 검토하되, 실제 호환성과 라이선스를 확인한 뒤 최종 결정하라.

- Frontend: React + TypeScript + Vite
- Styling: Tailwind CSS 또는 일관된 CSS 디자인 시스템
- Animation: Motion for React 또는 적합한 경량 애니메이션 도구
- Routing: React Router
- Server state: TanStack Query 또는 필요한 경우 Firebase SDK 중심의 간단한 구조
- Spreadsheet engine: HyperFormula 또는 요구사항을 충족하는 대안
- Spreadsheet UI: 적절한 오픈소스 스프레드시트 라이브러리 또는 자체 React 기반 그리드
- Backend services: Firebase Authentication, Cloud Firestore
- Hosting: Netlify
- Testing: Vitest, React Testing Library, Playwright
- Version control: Git

이것은 출발점이지 무조건적인 선택이 아니다.

스프레드시트 UI 라이브러리는 편집, 선택, 복사 및 붙여넣기, 다중 시트, 수식 계산, 가상 스크롤, XLSX 호환성, 라이선스를 검토한 뒤 선택하라.

예를 들어 Handsontable은 강력한 기능을 제공하지만 라이선스 조건을 확인해야 한다. HyperFormula 역시 현재 버전의 라이선스와 사용 조건을 확인하라.

라이브러리의 이름만 보고 Excel과 완벽히 호환된다고 가정하지 마라.

**비싼 상용 라이브러리를 별도 승인 없이 도입하지 말고, 라이선스가 불명확한 라이브러리를 핵심 구조에 의존시키지 마라.**

기술을 선택할 때는 다음 기준을 사용하라.

1. 실제 학습에 필요한 기능을 구현할 수 있는가?
2. 무료 또는 허용 가능한 라이선스로 사용할 수 있는가?
3. 프로젝트가 커져도 유지보수할 수 있는가?
4. 모바일 최적화보다 데스크톱 사용성에 집중할 수 있는가?
5. Firebase와 Netlify에 안정적으로 배포할 수 있는가?
6. 테스트하기 쉽고 확장 가능한가?

# 4. 서비스의 전체 정보 구조

다음 페이지를 중심으로 설계하라.

## 4.1 랜딩 페이지

첫 화면은 깔끔하고 전문적이어야 한다.

포함할 요소:

- 서비스 이름과 독자적인 로고
- 한눈에 이해되는 서비스 소개
- 실제 스프레드시트가 보이는 미리보기
- 학습 시작 버튼
- 학습 과정 소개
- 초급부터 고급까지의 성장 경로
- 자격증과 실무 학습 안내

과도한 장식이나 불필요한 애니메이션은 피하라.

## 4.2 대시보드

로그인 후 사용자가 가장 먼저 보는 화면이다.

다음 정보를 제공하라.

- 현재 학습 단계
- 이어서 학습하기
- 오늘의 목표
- 전체 학습 진행률
- 최근 학습한 내용
- 복습이 필요한 개념
- 틀린 문제 다시 풀기
- 완료한 도전 과제
- 최근 성취와 기록

사용자가 어디서부터 시작해야 하는지 고민하지 않도록 명확한 다음 행동을 제시하라.

## 4.3 학습 경로

모든 내용을 무조건 일직선으로 배치하지 마라.

개념 간의 선수 관계를 고려해 분기형 학습 경로를 설계하라.

예시:

- 스프레드시트 기초
- 셀과 데이터 입력
- 서식과 표
- 기본 수식
- 조건부 함수
- 데이터 정리
- 차트
- 데이터 분석
- 피벗 테이블
- 실무 자동화
- 컴퓨터활용능력 시험 대비
- 고급 문제 및 대회형 도전

각 단원은 다음 상태를 가질 수 있다.

- 잠김
- 학습 가능
- 학습 중
- 완료
- 복습 권장
- 마스터

사용자가 특정 개념을 충분히 이해했다면 복습 단계를 거쳐 다음 단원으로 이동하도록 설계하라.

다만 사용자의 진행을 불필요하게 막지 마라. 진단 평가, 선택적 선행 학습, 자유 연습 모드를 제공하라.

## 4.4 실제 학습 화면

이 화면은 서비스의 핵심이다.

일반적인 강의 페이지처럼 만들지 마라.

실제 스프레드시트 조작 환경을 중심으로 배치하라.

화면 구성 예시:

- 상단: 현재 단원, 진행 단계, 나가기
- 왼쪽: 학습 설명 및 단계별 안내
- 중앙: 실제 조작 가능한 스프레드시트
- 오른쪽: 문제 조건, 목표, 선택적 힌트
- 하단: 작업 상태, 실행 취소, 다시 시작, 필요에 따른 진행 버튼

화면 크기에 따라 배치를 조정하되, 데스크톱에서 충분한 작업 공간을 확보하라.

불필요하게 패널을 많이 만들지 마라. 사용자가 실제 작업에 집중할 수 있도록 하라.

## 4.5 연습실

사용자가 자유롭게 연습할 수 있는 공간이다.

- 빈 스프레드시트 만들기
- 샘플 데이터 불러오기
- 직접 셀 편집
- 수식 입력
- 여러 시트 사용
- 서식 및 차트 작업
- 실행 취소와 다시 실행
- 학습 파일 저장
- 지원하는 경우 XLSX 가져오기 및 내보내기

연습실과 정규 학습 모드는 분리하라.

연습실에서는 사용자의 자유를 보장하고, 학습 모드에서는 문제 목표와 채점 조건을 명확하게 제공하라.

# 5. 교육과정 설계

교육과정은 실제 능력을 기를 수 있도록 구성하라.

각 단계에서 설명, 시범, 안내형 실습, 독립 문제, 복습을 적절히 조합하라.

다음 교육 영역을 포함하라.

## Level 0 — 완전한 입문

- 스프레드시트란 무엇인가
- Excel과 Google Sheets의 기본적인 차이
- 통합 문서와 워크시트
- 행, 열, 셀, 셀 주소
- 셀 선택과 범위 선택
- 데이터 입력과 수정
- 복사, 붙여넣기, 삭제
- 자동 채우기의 기초
- 파일 저장과 관리

## Level 1 — 데이터 입력과 서식

- 텍스트, 숫자, 날짜
- 숫자 표시 형식
- 글꼴, 크기, 굵게, 색상
- 정렬, 테두리, 채우기
- 행 높이와 열 너비
- 셀 병합의 용도와 주의점
- 줄 바꿈
- 서식 복사
- 표의 가독성 개선

## Level 2 — 수식의 기초

- 수식의 기본 구조
- 연산자와 계산 우선순위
- 셀 참조
- 상대 참조
- 절대 참조
- 혼합 참조
- 수식 복사와 자동 채우기
- 괄호와 오류 이해
- 기본 산술 연산

## Level 3 — 핵심 함수

- SUM
- AVERAGE
- MIN, MAX
- COUNT, COUNTA
- IF
- AND, OR
- SUMIF, SUMIFS
- COUNTIF, COUNTIFS
- ROUND 계열
- IFERROR
- LEFT, RIGHT, MID
- LEN, TRIM
- CONCAT 및 TEXTJOIN
- 날짜와 시간 함수
- XLOOKUP 및 대안 함수
- INDEX와 MATCH
- FILTER, SORT, UNIQUE 등 지원되는 동적 배열 함수

각 함수는 정의만 알려주지 마라.

함수가 필요한 상황, 입력 인수, 반환값, 실제 업무 예시, 흔한 오류, 비슷한 함수와의 차이, 연습 문제를 함께 제공하라.

최신 Excel과 Google Sheets에서 지원하는 기능 및 버전 차이를 확인하라.

## Level 4 — 데이터 정리와 관리

- 정렬
- 필터
- 중복 데이터 처리
- 텍스트 나누기
- 찾기와 바꾸기
- 데이터 유효성 검사
- 드롭다운 목록
- 조건부 서식
- 표 기능과 구조화된 참조

공식적으로 확인되지 않은 대회 출제 경향을 사실처럼 주장하지 마라.

# 7. 튜토리얼 엔진

이 기능은 최우선 핵심 기능이다.

단순히 화면 위에 텍스트 상자를 띄우는 기능으로 끝내지 마라.

## 7.1 단계별 진행

각 튜토리얼은 여러 단계로 구성한다.

각 단계는 다음을 정의할 수 있어야 한다.

- 설명
- 강조할 UI 요소
- 강조할 셀 또는 범위
- 사용자가 해야 할 행동
- 허용되는 입력
- 완료 조건
- 실패 조건
- 힌트
- 다음 단계로 이동하는 조건
- 이전 단계로 돌아가는 방법
- 건너뛰기 가능 여부

단계는 코드가 아니라 선언적인 데이터로 정의하라.

예를 들어 사용자가 B2 셀에 `=SUM(B3:B7)`을 입력해야 하는 상황이라면, 실제 셀 편집 이벤트와 수식 계산 결과를 바탕으로 다음 단계로 넘어가야 한다.

설명 창의 '다음' 버튼을 눌렀다는 이유만으로 작업이 완료되었다고 처리하지 마라.

## 7.2 Spotlight와 말풍선

- 배경을 부드럽게 어둡게 만든다.
- 강조 대상은 원래의 가시성을 유지한다.
- 강조 대상 주변에 명확한 시각적 경계를 표시한다.
- 설명 말풍선은 대상과 연결한다.
- 화면 가장자리에서 말풍선이 잘리지 않도록 한다.
- 스크롤 또는 화면 크기 변경 시 위치를 다시 계산한다.
- 키보드와 마우스로 모두 사용할 수 있게 한다.
- 현재 단계와 전체 진행 상황을 표시한다.
- Esc 키의 동작은 단계 설정에 따라 명확하게 정의한다.

오버레이가 실제 입력을 막아서는 안 된다. 강조 대상만 적절히 조작할 수 있도록 포인터 이벤트와 키보드 이벤트를 설계하라.

셀 강조는 일반적인 DOM 요소 강조와 다를 수 있다. 가상화된 그리드에서도 안정적으로 동작하도록 셀 좌표와 화면 위치를 연결하라.

## 7.3 부드러운 애니메이션

다음 전환을 자연스럽게 설계하라.

- 단계 시작
- 강조 대상 변경
- 말풍선 위치 변경
- 성공
- 오류
- 힌트 공개
- 다음 문제
- 결과 화면

기본적인 전환은 짧고 자연스럽게 유지하라. 모든 요소가 동시에 튀거나 흔들리지 않게 한다.

과도한 탄성 효과, 불필요한 파티클, 긴 화면 전환은 피하라.

사용자의 작업을 방해하는 애니메이션은 사용하지 마라.

`prefers-reduced-motion`을 존중하고, 모션을 줄이는 설정을 제공하라.

애니메이션의 목적은 시각적 화려함이 아니라 사용자가 현재 상태와 다음 행동을 이해하도록 돕는 것이다.

# 8. 실제 스프레드시트 엔진

이 플랫폼은 단순한 표 모양의 모형이 되어서는 안 된다.

최소한의 핵심 동작을 실제로 구현하라.

## 8.1 기본 셀 조작

- 셀 선택
- 범위 선택
- 셀 편집
- Enter 및 Tab 이동
- 화살표 키 이동
- 행과 열의 기본 조작
- 복사 및 붙여넣기
- 실행 취소 및 다시 실행
- 셀 내용 삭제
- 자동 채우기
- 수식 입력줄
- 여러 워크시트
- 저장 가능한 셀 상태

## 8.2 수식 처리

수식은 직접 문자열을 비교하는 방식만으로 채점하지 마라.

수식 계산 엔진을 사용해 지원되는 함수와 셀 참조를 계산하라.

다음 기능을 지원 범위에 포함하라.

- 셀 간 참조
- 범위 참조
- 상대 참조와 절대 참조
- 여러 시트 간 참조
- 수식 오류 처리
- 의존 셀의 값 변경에 따른 재계산
- 지원 함수 목록
- 계산 결과 표시
- 함수별 오류 메시지

수식 입력 결과와 수식 자체를 구분해 저장하라.

가능하면 같은 계산 엔진을 학습 화면과 채점 시스템에서 공유하라.

브라우저에서 사용자가 입력한 수식을 `eval()`로 실행하지 마라.

지원하지 않는 함수나 기능은 명확하게 알리고, 임의의 결과를 반환하지 마라.

## 8.3 실제 Excel과의 차이

브라우저의 스프레드시트는 Microsoft Excel 자체가 아니다.

따라서 다음 원칙을 지켜라.

- 완벽한 Excel 호환성을 주장하지 않는다.
- 구현된 기능과 지원되지 않는 기능을 문서화한다.
- Excel 전용 기능과 Google Sheets 전용 기능을 구분한다.
- 함수 이름, 지역 설정, 날짜 처리, 오류 표시 등의 차이를 테스트한다.
- XLSX 가져오기 및 내보내기가 지원하는 기능과 제한을 안내한다.
- 자격증 시험의 실제 프로그램과 차이가 있는 경우 사용자에게 명확하게 알린다.

실제 Excel과 동일한 조작을 제공할 수 없는 기능은 기능을 흉내 내기만 하지 말고, 해당 기능을 가르칠 수 있는 대체 실습이나 외부 프로그램에서의 실습 안내를 제공하라.

# 9. 문제 풀이 및 채점 시스템

문제는 학습 엔진과 분리된 독립적인 콘텐츠여야 한다.

각 문제에는 다음을 정의하라.

- 문제 ID
- 난이도
- 목표
- 시작 데이터
- 초기 시트 상태
- 허용된 작업
- 기대 결과
- 채점 규칙
- 힌트 단계
- 오답별 피드백
- 풀이 설명
- 권장 해결 방법
- 대체 해결 방법
- 점수 규칙

## 9.1 정확한 채점

가능하면 단순한 정답 문자열 비교 대신 작업 결과를 검증하라.

예를 들어 문제의 목표가 A1:A10의 합계를 구하는 것이라면, 다음을 구분할 수 있어야 한다.

- 정확한 수식과 결과를 사용한 경우
- 다른 수식으로 같은 결과를 얻은 경우
- 숫자를 직접 입력해 우연히 같은 결과를 얻은 경우
- 수식이 올바르지만 범위가 잘못된 경우
- 결과가 현재 데이터에서는 맞지만 데이터가 바뀌면 틀리는 경우

문제의 교육 목표에 따라 허용할 답을 정의하라.

함수 사용 자체를 배우는 문제에서는 반드시 해당 함수나 개념을 사용하게 하고, 자유 해결 문제에서는 동등한 결과를 허용하라.

## 9.2 오답 처리

사용자가 잘못된 행동을 했다고 해서 무조건 전체 문제를 초기화하지 마라.

다음과 같이 설계하라.

- 단순한 입력 오류는 수정할 기회를 준다.
- 되돌릴 수 있는 작업은 Undo를 활용한다.
- 현재 단계에서 잘못된 행동은 구체적인 이유를 설명한다.
- 큰 오류가 발생하면 현재 단계 또는 마지막 안전 상태로 돌아갈 수 있게 한다.
- 사용자가 원하지 않는 한 작성한 데이터를 무조건 삭제하지 않는다.
- 문제를 다시 시작할 수 있게 한다.

실패는 벌을 주기 위한 장치가 아니라 학습 정보를 제공하는 장치여야 한다.

## 9.3 단계별 힌트

힌트는 사용자가 직접 요청했을 때 공개한다.

예시:

1. 첫 번째 힌트: 문제를 해결하는 데 필요한 개념.
2. 두 번째 힌트: 어떤 범위 또는 기능을 사용해야 하는지.
3. 세 번째 힌트: 수식의 구조나 작업 순서.
4. 마지막 도움: 완전한 풀이와 이유.

힌트를 열었다고 바로 문제를 끝내지 마라.

힌트를 보고도 사용자가 직접 입력하고 문제를 해결하도록 한다.

힌트 사용 횟수는 기록할 수 있지만, 학습을 지나치게 처벌하지 마라.

## 9.4 문제 다양성

같은 숫자와 같은 셀 주소만 바꾼 문제를 반복하지 마라.

문제 생성 시 다음 요소를 다양하게 조합하라.

- 데이터의 크기
- 데이터의 형태
- 조건의 개수
- 오류의 종류
- 사용해야 하는 개념
- 실무 상황
- 시간 제한
- 허용되는 해결 방법
- 데이터 품질
- 요구사항의 복잡성

문제의 난이도는 단순히 수식이 길다는 이유만으로 높게 설정하지 마라.

# 10. 실제 업무 데이터와 문제 콘텐츠

문제는 사용자가 실제 상황에서 판단하는 능력을 키워야 한다.

다음과 같은 데이터셋을 직접 설계하라.

- 판매 내역
- 상품 재고
- 고객 목록
- 지출 기록
- 출석 기록
- 주문 데이터
- 부서별 실적
- 날짜별 활동 데이터
- 오류가 섞인 데이터
- 여러 시트로 나뉜 자료

데이터는 단순하고 지나치게 규칙적이지 않도록 구성하라.

실제 업무에서 발견할 수 있는 빈 셀, 중복, 공백, 형식 불일치, 잘못된 날짜, 이상한 값 등을 포함할 수 있다.

단, 문제의 난이도에 맞지 않는 불필요한 혼란을 만들지 마라.

개인정보나 실제 기업의 기밀 데이터를 사용하지 말고, 독창적인 가상 데이터를 사용하라.

각 문제는 정답뿐 아니라 왜 그 방법이 좋은지 설명할 수 있어야 한다.

문제는 지속적으로 추가할 수 있어야 한다. 수백 개 이상의 문제를 목표로 확장할 수 있는 콘텐츠 구조를 마련하되, 검증되지 않은 문제를 숫자만 채우기 위해 생성하지 마라.

초기에는 검증된 핵심 문제를 충분히 완성한 뒤, 콘텐츠 제작과 검수 절차를 구축하라.

# 11. 게임화와 동기부여

게임화는 학습을 보조해야 하며 학습을 대체해서는 안 된다.

## 11.1 경험치

- 개념 학습
- 문제 해결
- 독립적으로 해결한 문제
- 복습 완료
- 프로젝트 완성
- 고난도 도전

등에 따라 경험치를 지급하라.

쉬운 문제만 반복해 경험치를 무한히 얻는 방식은 방지하라.

## 11.2 학습 연속 기록

매일 공부한 기록을 제공하되, 하루를 놓쳤다고 모든 성취가 사라지는 구조는 피하라.

학습 시간 자체보다 의미 있는 학습 활동을 기준으로 기록하라.

## 11.3 업적과 퀘스트

예시:

- 첫 수식 완성
- 첫 차트 만들기
- 절대 참조 이해
- 10문제 연속 해결
- 오답 복습 완료
- 첫 실무 프로젝트 완료
- 힌트 없이 고난도 문제 해결

업적은 실제로 달성한 행동을 기준으로 지급하라.

## 11.4 난이도 조절

사용자의 정답률, 문제 해결 시간, 힌트 사용, 오답 유형, 최근 복습 결과를 참고해 다음 문제의 난이도를 조절하라.

너무 쉬운 문제만 반복하지 말고, 지나치게 어려운 문제로 사용자를 좌절시키지도 마라.

기초가 약한 영역은 적절한 복습으로 돌아가게 하라.

## 11.5 복습 알고리즘

한 번 맞힌 문제를 영구적으로 완료 처리하지 마라.

틀린 문제, 힌트를 많이 사용한 문제, 오랫동안 복습하지 않은 개념을 적절한 간격으로 다시 제시하라.

간단한 간격 반복 알고리즘부터 시작해도 좋다.

복습 일정과 성취도는 사용자가 이해할 수 있는 방식으로 보여 줘라.

# 12. 사용자 인터페이스와 디자인 시스템

전체적인 인상은 전문적인 생산성 도구와 세련된 교육 플랫폼의 중간이어야 한다.

원하는 느낌:

- 깔끔함
- 차분함
- 명확한 정보 계층
- 정교한 간격
- 읽기 쉬운 타이포그래피
- 과도하지 않은 색상
- 부드러운 움직임
- 전문적인 업무 도구의 신뢰감
- 장시간 사용해도 피곤하지 않은 화면

게임처럼 보이기 위해 모든 요소를 화려하게 만들지 마라.

## 12.1 디자인 토큰

다음을 공통 토큰으로 관리하라.

- 색상
- 배경
- 텍스트 색상
- 경계선
- 그림자
- 여백
- 모서리 둥글기
- 폰트 크기
- 행 높이
- 애니메이션 시간
- 전환 곡선
- 상태별 강조 색상

컴포넌트마다 임의의 색상과 간격을 반복해서 정의하지 마라.

## 12.2 스프레드시트와 학습 UI의 분리

스프레드시트 그리드는 실제 작업 도구처럼 보여야 한다.

학습 UI는 그 위에서 작업을 안내하되, 그리드의 조작을 방해하지 않아야 한다.

표의 셀과 일반적인 카드 컴포넌트의 디자인을 혼합하지 마라.

선택된 셀, 편집 중인 셀, 수식 오류, 읽기 전용 셀, 목표 셀 등을 명확하게 구분하라.

## 12.3 반응형 정책

모바일 앱을 우선적으로 개발하지 마라.

우선순위는 다음과 같다.

1. 데스크톱과 노트북에서의 학습 경험
2. 일반적인 데스크톱 브라우저에서의 안정성
3. 작은 화면에서의 최소한의 접근성

좁은 화면에서는 핵심 작업을 수행하기 어려운 기능을 무리하게 압축하지 마라.

## 12.4 접근성

- 키보드만으로 주요 기능을 사용할 수 있어야 한다.
- 포커스 상태를 명확하게 표시한다.
- 색상만으로 정답과 오답을 구분하지 않는다.
- 충분한 대비를 제공한다.
- 적절한 ARIA 레이블을 사용한다.
- 애니메이션 감소 설정을 존중한다.
- 오류 메시지는 구체적이고 읽기 쉬워야 한다.

# 13. Firebase와 사용자 데이터

Firebase는 실제 사용자 계정과 학습 진도를 관리하는 데 사용한다.

## 13.1 인증

필요한 경우 다음 기능을 지원하라.

- 회원가입
- 로그인
- 로그아웃
- 비밀번호 재설정
- 사용자 프로필
- 학습 진도 불러오기
- 다른 기기에서의 진도 동기화

인증 없이 이용할 수 있는 체험 모드도 고려하라.

## 13.2 데이터 모델

다음 데이터를 적절하게 분리해 저장하라.

- 사용자 프로필
- 학습 설정
- 단원 완료 상태
- 문제 풀이 기록
- 문제별 정답률
- 힌트 사용 내역
- 복습 일정
- 경험치와 업적
- 연속 학습 기록
- 사용자별 저장 문서
- 설정 및 선호도

사용자별 문서 ID, 접근 권한, 쿼리 비용, 데이터 증가량을 고려하라.

문제 콘텐츠는 버전 관리가 가능한 공용 데이터로 관리하고, 사용자별 학습 기록과 분리하라.

## 13.3 보안

Firebase 보안 규칙은 필수다.

- 로그인한 사용자는 자신에게 허용된 데이터만 읽고 쓸 수 있어야 한다.
- 다른 사용자의 개인 데이터를 접근하거나 수정할 수 없어야 한다.
- 사용자 ID를 클라이언트가 임의로 바꿔 다른 사용자의 데이터에 접근할 수 없어야 한다.
- 경험치나 업적을 조작하기 쉬운 구조를 피한다.
- Firebase Admin SDK의 비밀 키를 프런트엔드에 포함하지 않는다.
- API 키와 비밀 정보의 성격을 구분하고 필요한 제한을 적용한다.
- 필요한 경우 서버 측 검증을 사용한다.
- 실제 비밀 값은 환경 변수로 관리한다.

Firestore 보안 규칙은 단순히 로그인 여부만 확인하는 방식으로 끝내지 마라.

실제 권한 검증 테스트를 작성하라.

## 13.4 비용과 안정성

Firestore 읽기·쓰기 횟수, 리스너 사용, 데이터 용량, 인덱스, 요청 빈도를 고려하라.

불필요하게 모든 문제 데이터를 매번 불러오지 마라.

Firebase가 일시적으로 연결되지 않더라도 가능한 경우 현재 학습 상태를 유지하고, 저장 실패를 사용자에게 명확히 알려라.

# 14. Netlify 배포

최종적으로 Netlify를 통해 실제 웹사이트를 배포할 수 있어야 한다.

다음 작업을 수행하라.

- 개발 환경 설정
- 프로덕션 빌드
- 환경 변수 설정
- SPA 라우팅 설정
- Firebase 연결
- HTTPS 환경에서의 동작 확인
- 배포 후 주요 페이지 테스트
- 브라우저 콘솔 오류 검사
- 새로고침 후 라우팅 확인
- 로그인 상태 유지 확인
- 학습 진도 저장 및 복원 확인

환경 변수 예시는 `.env.example`에 제공하되 실제 비밀 값을 포함하지 마라.

`.env.local`이나 비밀 정보가 포함된 파일을 Git에 커밋하지 않도록 `.gitignore`를 확인하라.

Firebase 프로젝트가 아직 준비되지 않았다면 개발 모드에서 로컬 데이터로 작동하도록 만들고, Firebase 설정이 필요한 부분을 명확하게 문서화하라.

배포 과정에서 문제가 발생하면 실제 오류를 해결하라. 단순히 배포 방법만 설명하고 끝내지 마라.

# 15. 파일 구조와 코드 품질

컴포넌트를 하나의 거대한 파일에 몰아넣지 마라.

관심사에 따라 명확하게 분리하라.

예상 구조:

src/
  app/
  components/
    ui/
    layout/
    spreadsheet/
    tutorial/
    feedback/
  features/
    learning/
    practice/
    progress/
    achievements/
    authentication/
    certification/
  engine/
    spreadsheet/
    grading/
    tutorials/
    review/
  content/
    courses/
    lessons/
    exercises/
    datasets/
  services/
    firebase/
    storage/
  hooks/
  lib/
  types/
  styles/

이 구조는 예시다. 실제 프로젝트의 크기와 복잡성에 맞게 조정하라.

다음 원칙을 지켜라.

- TypeScript의 엄격한 타입 검사를 사용한다.
- `any`를 남용하지 않는다.
- 중복 코드를 줄인다.
- 컴포넌트와 비즈니스 로직을 분리한다.
- 공통 상태 관리 전략을 정한다.
- 오류 처리 방식을 통일한다.
- 로딩, 빈 상태, 오류 상태를 구현한다.
- 개발 전용 코드를 프로덕션에 노출하지 않는다.
- 사용하지 않는 의존성을 추가하지 않는다.
- 기능이 없는 버튼을 만들지 않는다.
- 화면만 구현하고 실제 동작을 미루지 않는다.

프로젝트가 필요 이상으로 복잡해지지 않도록 단순한 구조를 우선하되, 스프레드시트 엔진과 채점 엔진은 확장할 수 있게 설계하라.

# 16. 테스트와 품질 검증

실제로 동작하는지 검증하지 않은 기능을 완료했다고 보고하지 마라.

## 16.1 단위 테스트

다음 영역을 테스트하라.

- 수식 계산
- 셀 참조
- 채점 규칙
- 힌트 단계
- 튜토리얼 진행 조건
- 학습 완료 조건
- 경험치 계산
- 복습 일정
- 데이터 저장 및 복원

## 16.2 통합 테스트

- 스프레드시트 입력과 수식 계산
- 실제 작업 결과와 문제 채점
- 문제 완료와 학습 진도 저장
- Firebase 로그인과 사용자 데이터 접근
- 튜토리얼과 셀 조작의 연결
- 오류 발생 후 재시도
- Undo와 다시 실행

## 16.3 브라우저 테스트

Playwright 등을 이용해 실제 브라우저에서 다음을 확인하라.

1. 사용자가 첫 화면에서 학습을 시작할 수 있는가?
2. 첫 튜토리얼이 정상적으로 표시되는가?
3. 사용자가 셀을 선택하고 편집할 수 있는가?
4. 수식이 계산되는가?
5. 올바른 답이 채점되는가?
6. 잘못된 답에 적절한 피드백이 제공되는가?
7. 힌트가 요청했을 때만 공개되는가?
8. 문제를 완료한 뒤 다음 문제로 이동하는가?
9. 새로고침 후 진도가 유지되는가?
10. 브라우저 콘솔에 심각한 오류가 없는가?

테스트가 실패하면 원인을 찾아 수정한 뒤 다시 실행하라.

# 17. MVP 구현 순서

처음부터 모든 기능을 구현하려고 하지 마라.

가장 중요한 핵심 기능을 실제로 완성하고 검증한 뒤 확장하라.

## Phase 1 — 프로젝트 기반

- 프로젝트 구조 확인
- 기술 스택 확정
- 디자인 토큰
- 공통 UI 컴포넌트
- 라우팅
- 랜딩 페이지
- 대시보드 기본 구조

완료 조건: 프로젝트가 정상적으로 실행되고 빌드된다.

# 18. 작업 방식

Claude Code는 프로젝트를 실제로 수정하는 개발 도구로 사용한다.

다음 규칙을 준수하라.

1. 현재 파일과 환경을 먼저 확인한다.
2. 이미 존재하는 프로젝트를 불필요하게 초기화하지 않는다.
3. 작업 전에 구현 계획과 중요한 기술적 결정을 정리한다.
4. 가능한 한 실제 파일을 작성하고 수정한다.
5. 기능별로 실행하고 테스트한다.
6. 오류가 발생하면 해결하고 다시 검증한다.
7. 작업하지 않은 기능을 완성했다고 주장하지 않는다.
8. 라이선스가 불확실한 의존성은 먼저 확인한다.
9. 실제로 존재하지 않는 API나 라이브러리 기능을 가정하지 않는다.
10. 보안 규칙과 환경 변수 설정을 생략하지 않는다.
11. 중요한 설계 결정은 문서로 남긴다.
12. 장기적으로 유지보수할 수 있는 코드를 작성한다.

작업 중 매번 계획만 길게 설명하고 멈추지 마라.

합리적인 기본값으로 진행할 수 있는 부분은 직접 결정하고 구현하라. 단, Firebase 프로젝트 생성, 계정 인증, 비밀 값 설정 등 사용자의 외부 작업이 필요한 경우에는 정확한 설정 방법을 안내하라.

큰 작업은 작은 단계로 나누고, 각 단계가 완료될 때 실제로 검증하라.

# 19. 최종 완성 기준

다음 기준을 충족하지 못하면 프로젝트를 완성했다고 보고하지 마라.

- 독자적인 브랜드와 일관된 디자인이 있다.
- 데스크톱에서 사용하기 편하다.
- 학습 경로가 명확하다.
- 실제 셀을 편집할 수 있다.
- 지원되는 수식이 정상적으로 계산된다.
- 튜토리얼이 실제 사용자 행동과 연결된다.
- 힌트는 요청했을 때만 제공된다.
- 오답을 이해하고 다시 도전할 수 있다.
- 채점 결과가 정의된 규칙과 일치한다.
- 학습 진도와 복습 기록이 관리된다.
- Firebase 보안 규칙이 검증된다.
- Netlify에 배포할 수 있다.
- 핵심 기능의 자동화 테스트가 통과한다.
- 지원하지 않는 기능을 명확하게 표시한다.
- 실제 Excel과의 차이를 정직하게 안내한다.
- 새로운 문제와 단원을 추가하기 쉽다.

최종 보고서에는 다음을 포함하라.

- 구현된 기능
- 아직 구현되지 않은 기능
- 사용한 기술과 선택 이유
- 실행 및 배포 방법
- 환경 변수 목록
- Firebase 설정 방법
- 테스트 결과
- 알려진 제한사항
- 다음 개발 단계

# 20. 지금 당장 시작할 작업

이 프롬프트를 읽은 뒤 모든 요구사항을 한 번에 구현하려고 하지 마라.

먼저 다음을 수행하라.

1. 현재 작업 디렉터리와 프로젝트 상태를 확인한다.
2. 공식 문서와 기술적 제약을 바탕으로 핵심 기술을 선택한다.
3. `docs/PRODUCT_SPEC.md`에 제품 요구사항을 정리한다.
4. `docs/TECHNICAL_DESIGN.md`에 아키텍처와 데이터 흐름을 정리한다.
5. `docs/CURRICULUM.md`에 전체 교육과정의 구조를 정리한다.
6. `docs/IMPLEMENTATION_PLAN.md`에 단계별 구현 계획과 완료 조건을 기록한다.
7. 첫 번째 MVP의 범위를 확정한다.
8. 곧바로 실제 프로젝트의 기반 구현을 시작한다.

처음부터 모든 함수, 모든 자격증 문제, 모든 고급 기능을 구현할 필요는 없다.

**가장 먼저 완성해야 하는 것은 하나의 개념을 설명하고, 실제 스프레드시트에서 직접 연습하고, 정답을 검증하고, 오답을 수정한 뒤, 다음 문제로 자연스럽게 넘어가는 완전한 학습 경험이다.**

이 경험이 완성되면 동일한 엔진을 이용해 수백 개의 개념과 문제로 확장할 수 있어야 한다.

마지막으로, 이 프로젝트의 목표는 화려한 화면을 만드는 것이 아니다.

사용자가 이 사이트에서 꾸준히 공부한 결과 실제 Excel과 Google Sheets를 더 잘 사용할 수 있고, 업무와 시험에서 스스로 문제를 해결할 수 있게 만드는 것이다.

모든 기술적·디자인적 선택은 이 목표를 기준으로 판단하라.

이제 프로젝트를 조사하고, 설계하고, 실제 구현을 시작하라.
